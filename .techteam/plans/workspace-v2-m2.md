## 2. Expected State

**One provider contract, three providers, ten roles — Codex present but unable to build.**

```ts
type ProviderId = 'claude' | 'cursor' | 'codex';            // registry-driven; no ternaries on names anywhere
interface Capabilities {
  readOnly: boolean; build: boolean; structuredOutput: 'native' | 'prompted';
  webResearch: boolean;                                      // has web tools at all
  readOnlyIsolation: 'verified' | 'partial' | 'unverified';  // fail-closed predicate | known weaker tier (Cursor) | none yet
  buildIsolationVerified: boolean;                           // live no-push suite passed for this provider
  webResearchIsolated: boolean;                              // per-profile tool lock-down proven (M5)
  limitSignal: 'event' | 'cli-text' | 'none'; resume: boolean;
}
interface Provider {
  id; label; detect(cfg): Promise<Detect>;                   // missing | broken-install | ok  (+ version/path/hint)
  auth(cfg): Promise<Auth>;                                  // ok | not-logged-in | unknown
  selfTest(cfg, level: 'cheap' | 'canary'): Promise<SelfTest>;   // 'canary' may spend quota ⇒ explicit confirmation
  capabilities(cfg): Capabilities;
  runReadOnly(req): Promise<AgentResult>;
  build?: { prepare(ctx): Promise<BuildPrep>; run(req, prep): Promise<AgentResult>; verifyGuard(prep, ctx): Promise<{ ok: boolean; detail: string }> };
}
```

- **Build envelope is provider-agnostic and mandatory** (`src/pipeline/envelope.ts`, extracted from `stages.build` with zero behaviour change): git no-push env, `snapshotGitMeta/revertGitMeta`, `commitAll` secret/scope guard, `postBuildChecks`, redaction, allow-listed child env. The provider only adds its *own* guard through `prepare` (e.g. Cursor writes `.cursor/cli.json`, hash recorded) and `verifyGuard` (hash check). The `Run` fields become generic (`guardSha`, `guardEnvOnly`; migrated from `cursorGuardSha/noPushEnvOnly` by a run.json migration).
- **Roles** (`requirements, context, planning, architecture, implementation, review, verification, debugging, documentation, research`): `config.roles[role] = { providers: ProviderId[], autoByComplexity?: { S?, M?, L? } }`. Defaults reproduce v1 exactly: planning/review/verification → `[claude]` + (`cursor` appended iff v1 `onClaudeLimit==='cursor'`, the v1 default); implementation/debugging → `[cursor]`; requirements/context/architecture/research → `[claude]`; documentation → `[cursor]`. **Codex appears in no default chain (D8).** In M2 the engine executes the four existing stage slots (planning, review, verification, implementation; fix loops = debugging); the other roles are validated, stored, and consumed by M3–M5 (an item's `role`).
- **Routing** (`src/agents/routing.ts`, pure): `chain(role, {complexity?, health, pauses, caps})` → ordered candidates: complexity pick first when configured (applies to stages that run **after** the plan is known: review, implementation, verification, debugging — planning uses its fixed chain; a pre-plan estimate is M3), then configured order; drops providers that are missing/broken/not-logged-in/paused unless nothing else remains (then the stage pauses with the exact reason — v1 usage-limit pause semantics unchanged); **filters by capability**: a role needing `build` only admits `build && buildIsolationVerified` providers; `research` only `webResearchIsolated`; read-only roles admit `readOnly` providers of any isolation tier but the UI/run log label `partial/unverified` tiers. Running a stage: first candidate, on `limit` / `spawn` / `auth` error advance to the next, with a visible note (v1's "Cursor takes over read-only stages" is exactly this, now general). **A fallback never promotes a provider whose build isolation is unproven.**
- **Validation of assignments** (`PUT /api/roles`, whitelist-only, clamped, unknown keys ignored — same pattern as `PUT /api/settings`): pairing check against capabilities with a human reason, e.g. "Codex cannot own *Implementation*: its no-push isolation has not been verified on this machine."

  - **Authentication never links or copies the user's own `~/.codex/auth.json`** (Reviewer blocker 5: Codex writes refreshed tokens back to `auth.json` — likely temp-file + rename, which would replace a symlink with a divergent file and leave the user's real login with a rotated-out token; and Conductor runs concurrently with the user's interactive Codex; the vendor says not to share one `auth.json` across concurrent jobs). Two supported modes only: **(a) a separate login into the private home** — the wizard shows the exact command for the user to run themselves (`CODEX_HOME=~/.conductor-v2/providers/codex-home codex login`; Conductor never types credentials or runs the login for them), after which `auth()` = `codex login status` against the private home; or **(b) `CODEX_API_KEY`** stored via the secret store and injected into that one child's env only (never argv/logs; `CODEX_API_KEY` is the documented mechanism for `codex exec`). The private home is mode 0700, `auth.json` 0600.

No attempt ⇒ **inconclusive ⇒ `unverified`**, never pass (a model may simply not try). Hook/MCP canaries must have a **side effect** — the canary hook script / MCP server touches a marker file — and "not honoured" = marker file **absent**; absence of transcript events proves nothing because Codex may emit none for hooks. Not runnable today (binary broken) ⇒ Codex stays `unverified`; reported **"not run"**.

A parse-level flag probe can show a flag is *recognised*, not that a `-c` pin took effect (unknown `-c` keys are typically accepted), so it is not offered as verification; **the docs must not say the pinned flags are verified** until the behavioural canary has run against a working binary. Anything that would reach the model is `canary`.

## 2b. Security design conditions — BINDING (Security sign-off `workspace-v2-m2-security-design.md`, "Approved with conditions"; the Reviewer checks the diff)

1. **Envelope design (A-1…A-7).** (a) A single `runBuild()` in `pipeline/envelope.ts` is the **only** code path that can start a builder; `provider.build.run` is not exported to other modules; a static test asserts `runCursor`/`build.run` appear only in the Cursor adapter and the envelope. (b) The `build && buildIsolationVerified` gate is **re-asserted inside `runBuild()`** against the provider registry and the verification store/code baseline — never against config or anything the adapter self-reports. (c) `Capabilities.build` is **derived from `typeof provider.build === 'function'`**, `buildIsolationVerified` only from the verification store / code baseline; in M2 `registry.codex.build === undefined` (test). (d) `verifyGuard`/`prepare` fail **closed**: a throw, a rejected promise, or a missing hook for a provider that declared a guard ⇒ `ok:false` ⇒ `needs_human`; env merge order `providerEnv < extraEnv < envelope env`, and `GIT_*`, `HOME`, `PATH`, `CODEX_HOME`-class keys returned by `prepare` are dropped. (e) **Meta restore moves into a `finally`** (provider throws / limit / abort / timeout all restore hooks and `core.hooksPath`) — declared in the commit message as the one intentional behaviour difference. (f) **Characterization tests first (commit 1a):** `test/envelope.test.ts` is written and green against the CURRENT code path, then passes unchanged after extraction; cases: hook installed by the builder; `core.hooksPath`/alias/pushurl changed; guard file modified/deleted; secret in a committed file; protected file changed but not in the plan; builder self-commits a protected file; rename of a protected source; provider `run` throws; `verifyGuard` throws; `prepare` tries to override `GIT_CONFIG_GLOBAL`; limit/abort/timeout results; provider without `prepare`. (g) run.json migration `cursorGuardSha→guardSha`, `noPushEnvOnly→guardEnvOnly` carries old values and defaults `guardEnvOnly` to **true** when neither exists; the API keeps `noPushEnvOnly` as a derived view; `guardEnvOnly` stays a first-class field (M6 policy will key on it). (h) The tracked-`.cursor/cli.json` ⇒ env-only behaviour is preserved bit-for-bit (A-8). (i) The provider **label** comes from the registry in the commit trailer ("Built by Conductor (<label>)") and in failure notes (A-9).
2. **Codex exec configuration (B-1, B-3).** No reliance on the private `config.toml` at exec time; **all pins are flags or `-c`**; `config.toml` is login-time only (credential store), written by Conductor, hash-checked and rewritten before every run, with no MCP servers/hooks; the wizard's login command states the credential store explicitly and `auth()` reports `not-logged-in` with guidance when no file credential exists. The argv builder is **constants-only** and a test asserts the **absence** of `--dangerously-bypass-approvals-and-sandbox`, `--yolo`, `--full-auto`, `--approve-for-me`, `--add-dir`, `--search`, `--profile`/`-p`, any `workspace-write`/`danger-full-access` string and any user- or config-derived `-c`. The only config-derived value is `agents.codex.model`, validated `^[A-Za-z0-9][A-Za-z0-9._:/-]{0,63}$` and passed as `--model=<v>`. `--skip-git-repo-check` only for the canary scratch dir, never for stage runs. `--ignore-rules` is kept (B-2) and has its own canary item.
3. **Environment / secret policy (B-4, B-6c, E-5).** Pin `shell_environment_policy` via `-c` (minimal inherit, `ignore_default_excludes=false`, excludes for `CODEX_*`, `*KEY*`, `*TOKEN*`, `*SECRET*`) **and prove it with the decoy canary**; if it cannot be proven, **API-key mode is not offered** (login mode only). The Codex child gets `HOME` pointing at a **private empty directory**. `CODEX_API_KEY`, if offered: entered through a setup route/CLI that follows the old key-route pattern (shape check, never echoed, stored via `secrets.ts`, rate-limited), registered as an exact-match redaction secret in log config and `engine.secrets()`, and **never** in argv, any child env other than that one Codex run, prompt audit files, run events, logs, `/api/providers`, `/api/state` or error bodies (a test per sink).
4. **Canary specification (B-8, B-9).** Order: **positive control first** (the same hook/MCP/AGENTS.md items placed so they SHOULD load must create the marker — otherwise absence is meaningless ⇒ inconclusive); **project-layer code-execution canary** (scratch repo with `.codex/config.toml` MCP + hook and `.codex/rules/canary.rules` allow-rule, each with a marker side effect; any marker ⇒ **FAIL ⇒ `blocked`**); **network canary** (loopback listener; pass only with an attempted command and no connection); **environment canary** (decoy `CONDUCTOR_CANARY_DECOY_KEY=<random>`; pass only if an attempted command's output lacks it); **credential-read disclosure** (informational tier note "can read outside the repo", never pass/fail); hygiene: unique nonce per marker, marker dir outside every writable root, scratch cwd per run, fake `HOME`, cleanup, per-call confirmation with an explicit cost/quota statement; parsing of undocumented events defaults to **inconclusive on any ambiguity**. **Result binding:** `{cliVersion, binary sha256 when resolvable, argv-pin digest, private-config sha256, canaryVersion, passedAt, evidence summary}`; any change invalidates it; **`blocked` is sticky** until a later pass. **Explicit `minVersion`** in the registry (taken from the vendor changelog): below it Codex is `unverified` and the canary refuses.
5. **Verification trust model (D-1…D-3).** Cursor's baseline is a **code constant** `{cliVersion:'2026.10.19', grandfathered:true, source:'bundled-repo-suite'}`, not a file; the file can only **add** records (corrupt/absent/invalid ⇒ "no record", never a downgrade below the baseline and never an upgrade); **no HTTP route and no canary result can write `buildIsolationVerified`** (the canary only writes the read-only tier); record fields: `provider`, `suite` + `suiteDigest`, `cliVersion`, `binSha256` when resolvable, `passedAt`, `source` in a closed enum, `grandfathered` honoured only when the code baseline asserts it; file 0600 / dir 0700 / lstat regular / owner = user; HMAC keyed from the secret store where a keychain exists (tamper evidence, documented as such); validated at every use against the CURRENT version/binary hash, mismatch ⇒ unverified (Cursor: allowed with a persistent banner on the run summary and the provider card). The read-only tier result is persisted with the same binding; a stale/invalid file reads as `unverified`. M2 states plainly that **Codex has no `build` by construction**.
6. **Routing rules (C-1…C-4, C-6, C-7).** Limit/auth/spawn classification only after a **structural failure** is established (non-zero exit or terminal `turn.failed`/`error`, and **no `turn.completed`**), applied to the structured error message capped at 500 chars, then stderr; a run with exit 0 and `turn.completed` can never be reclassified by prose. Complexity routing may **never lower the isolation tier** (only equal-or-better tier than the chain head for review/verification; only `build && verified` for build roles; `PUT` also rejects an ineligible complexity entry). A static exhaustive **`ROLE_NEEDS: Record<Role,{build?:true; research?:true}>`** (a new role without an entry fails to compile); **`documentation` is build-class**. "Unless nothing else remains" **never runs an ineligible provider** (only-ineligible chain ⇒ pause with the reason, zero spawns). Provider pauses derived from a limit message have a **24 h ceiling** with the human resume path kept. Routing is a **pure function of exactly**: config chains, CLI-reported health/auth, CLI-reported limit events, capabilities from code/stores, and plan complexity — with a test. Each chain advance leaves a visible run note + board comment; assigning a provider to a role shows the data-egress statement once.
7. **API rules (E-1…E-4, E-6).** `:id` is checked against the `ProviderId` registry **before any path is built**; strict body typing (a plain object is required — `null`/array/primitive rejected); role names checked with `Object.hasOwn(ROLE_NEEDS, role)` and stored in a null-prototype object/`Map` (`__proto__`/`constructor` roles are inert); `providers` entries are registry ids, de-duplicated, length-capped; `autoByComplexity` keys `S|M|L` only and through the same pairing check; the **capability filter re-runs when the config is loaded** (hand-edited/migrated config is untrusted: ineligible entries are dropped with a warning); `canary` needs `confirm === true` **on every call**, single-flight per provider with a cooldown, sharing the per-home mutex with engine runs, refused while a stage of that provider is running; assigning an `unverified` provider needs an explicit acknowledgement field, a `blocked` one is rejected with the reason; every CLI-originated string in `GET /api/providers` is redacted, truncated, rendered with `textContent`, and the repair hint is a **static** string per provider; `doctor --isolation codex` / `--verify-build` require `--yes` (they spend quota).

## 6. Risks and Dependencies

- **Extraction risk** (moving the guard lifecycle): mitigated by commit-1 "no behaviour change" rule, argv snapshot, unchanged tests, live suites.
- **Codex flags are unverified** (`-c` keys, stdin `-`, `--ephemeral` semantics, `approval_policy` key name, `sandbox_workspace_write.network_access`): `-c` pins are *belt-and-braces* only; the real controls are the first-class `--sandbox read-only` flag, the private `CODEX_HOME`, and the **behavioural** canary. A *failed* canary ⇒ `blocked` (unselectable); an *unavailable/not-run* canary ⇒ `unverified` (selectable, labelled); no silent fallback to unpinned defaults.
- **Private `CODEX_HOME` credentials:** separate login in the private home or `CODEX_API_KEY` — never the user's own `auth.json` (blocker 5). If keyring storage is forced by a future Codex default, the pinned `cli_auth_credentials_store = "file"` plus an `auth()` probe surfaces it as `not-logged-in` with guidance rather than silently using the keyring.
- **Read-only isolation of Codex/Cursor is weaker than Claude's** (no tool inventory to check, cannot deny credential reads): documented tier, redaction mandatory on all outputs, Cursor behaviour unchanged.
- **Quota use:** `selfTest('canary')` and live suites spend provider quota → explicit confirmation, never automatic.
- **Dependencies:** M1 (board; roles/items), a working Codex binary for live verification (user permission to repair).
- **Assumptions:** `AgentName` rename is mechanical; UI shows provider chips from the registry.
