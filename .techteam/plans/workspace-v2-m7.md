## 1. Current State (verified in the clone at `bd5f186`)

- **Zero-runtime-dependency Node ≥ 22.18 app** started as `node bin/conductor.mjs start`; TypeScript runs by type stripping; the UI is static files served by the loopback server (OTP login, session cookie, CSRF).
- **macOS-only edges:** secrets in the macOS Keychain via the `security` CLI with a 0600 file fallback (`secrets.ts`); background service = launchd (`service.ts`, v2's own label); notifications via `osascript` (`notify.ts`); "open" via `/usr/bin/open` and a POSIX `SAFE_PATH`/`searchPath` (`config.ts`, `cli.ts`, `server/open.ts`); the control channel is a unix socket (`paths.control`, `http.ts`); path checks use `startsWith('/')` (`api.ts`, `config.ts validRepo`); child processes use POSIX tools: gates and dependency installs run through `sh -c` (`git/gates.ts`, `git/worktree.ts`), the no-push env uses `/usr/bin/false` and `/dev/null` (`agentGitEnv`, `GIT_CONFIG_GLOBAL`), process groups via `kill(-pid)` (`agents/spawn.ts`), the child env allow-list carries POSIX keys only (`agents/env.ts`).
- **No packaging at all:** no Electron shell, no installer, no CI definition, no diagnostics export, no tray/background behaviour definition, no secret inventory document.
- **Environment (verified earlier today):** macOS arm64, Node v22.21.1, Docker present, wine absent; Electron/electron-builder not installed (and not to be installed without permission).

## 2. Expected State

**Conductor can be built into (a) an Electron desktop app that runs the existing server as a sidecar and presents the same dashboard, and (b) a Windows installer and a Debian package — with the platform differences isolated behind one strategy layer, every OS-specific safety property re-established per OS, and each artifact labelled with exactly what was and was not verified.**

### 2.1 Delivery in three sub-milestones (each reviewable, each ends green)

- **M7a — cross-platform strategy layer + build-to-`dist`** (no new dependency, no download): the runtime gains `src/platform/{index,posix,win32}.ts` behind one interface and the app can be built into a self-contained `dist/` that runs with only Node. Everything verifiable on macOS (and Linux via a container if Docker is allowed) is tested here.
- **M7b — Electron shell** (needs the download permission): `desktop/` main + preload + sidecar management, hardened per F-9, with a unit-testable core and a scripted smoke run.
- **M7c — packaging + CI + diagnostics + docs** (needs the download permission for builder tooling/images): electron-builder config for NSIS (`.exe`) and `.deb`, the build run in a Docker image (Docker is present; wine is not), a smoke test of the `.deb` in a container, written-but-unexecuted CI YAML, the diagnostics export, and the secret inventory.

### 2.2 Strategy layer (M7a) — what is abstracted and how each OS behaves

| Concern | POSIX (macOS/Linux) | Windows (preview) |
| --- | --- | --- |
| Secret store | macOS Keychain via stdin (unchanged); Linux: `secret-tool` (libsecret) if present else the 0600 file store with a visible notice | DPAPI-backed encrypted file via a PowerShell-free route is not possible without a native module → **v2 stores no credentials today (§2b-2)**; the `safeStorage` plumbing is built only when the first stored secret exists; until then the true secret inventory (env passthrough, session OTP/cookie/CSRF, the CLIs' own stores) is written and tested |
| Process runner for gates/installs | `sh -c` as today (explicit, documented) | **no `shell:true` and no `cmd /c` with agent- or schema-derived text:** gate/install commands are split into argv by a strict tokenizer or run from a temp script file written by Conductor (`.cmd`/`.ps1` generated from the validated command, never from model text); `.cmd` shims resolved to the underlying executable via `PATHEXT`; if a command cannot be run safely it is refused with the reason |
| No-push git env | `GIT_CONFIG_GLOBAL=/dev/null`, `GIT_ASKPASS=/usr/bin/false` | `NUL` and a generated stub executable; **the no-push guard self-test (`doctor`) must exercise the guard on the host OS** — a platform whose self-test cannot run is reported unverified; building on Windows/Linux is disabled by code until that platform has its own committed evidence (§2b-1), and a host record can only restrict further |
| Process tree kill | `kill(-pgid)` | `taskkill /T /F /PID` |
| Child env allow-list | POSIX keys | + `USERPROFILE, APPDATA, LOCALAPPDATA, SystemRoot, SystemDrive, PATHEXT, TEMP, TMP, COMSPEC`; never `shell:true` |
| Paths | POSIX checks | `path.isAbsolute` + drive/UNC rules everywhere `startsWith('/')` is used; reserved device names refused |
| Control channel | unix socket 0600 | **none in desktop mode** (the dashboard server is the only channel); a named pipe only with an explicit restrictive DACL — not built in v2.0 |
| Background service | launchd (own label) | desktop: tray + sidecar (§2.4); no native Windows service (out of scope) |
| Notifications / open | `osascript` / `open`, `xdg-open`, `notify-send` | Electron `Notification` and `shell.openExternal` (https-only) in the app; PowerShell toast **not** used |
| Worktrees | `<repo parent>/.conductor-v2-worktrees` | the same layout with Windows path limits checked (long-path refusal with a reason) |

The strategy is selected once at startup; every function has a POSIX implementation identical to today's behaviour (the existing suite must pass unchanged on macOS — extraction gate), and the Windows implementations are unit-tested **as pure logic** (tokenizer, env builder, path rules, command-file generation) on any host and are **not** claimed to work on Windows.

### 2.3 Electron shell (M7b) — binding hardening (F-9)

- **Process model:** main process (window, tray, IPC, `safeStorage`), a hardened renderer loading the loopback dashboard, and a **sidecar** running the existing server via `utilityProcess` (preferred over `ELECTRON_RUN_AS_NODE`; if the latter is kept, the reason and the RunAsNode fuse are recorded).
- **Session without new surface (§2b-5):** the sidecar binds `127.0.0.1` port **0**, mints one OTP and sends `{port, otp}` to main over the `utilityProcess` MessagePort; main loads `http://127.0.0.1:<port>/auth` with `loadURL(…, {postData: [rawData "otp=<otp>"], extraHeaders: form content type})` — the **existing `POST /auth`** route; the OTP never appears in a URL or on any command line. **No new HTTP route, no static token.**
- **BrowserWindow:** `contextIsolation: true`, `sandbox: true`, `nodeIntegration: false`, `webviewTag: false`; `will-navigate` and `setWindowOpenHandler` locked to the exact loopback origin; `shell.openExternal` accepts `https:` only; permission handler denies everything; a dedicated session partition; a strict CSP (the server already sends one); no remote code or content.
- **Secrets:** `safeStorage` is reachable from the **main process only** (never exposed through preload) and delivered to the sidecar over IPC; one policy: **refuse silent plaintext** — an explicit consent screen when the backend is `basic_text`; a written **secret inventory** (what is stored, where, how injected, how redacted).
- **Single instance, crash behaviour, update policy:** one instance lock; the sidecar restarts with the existing crash-recovery path; **no auto-update** in v2.0 (documented).

### 2.4 Background execution and diagnostics (M-5)

- **Window close → tray, sidecar keeps running** (a native OS service is out of scope). Quit from the tray stops the sidecar gracefully and relies on the existing crash recovery for anything in flight; documented and tested at the sidecar-manager level.
- **Diagnostics export** (user-triggered, file chosen by the user): redacted logs, versions (app, Node/Electron, CLIs), provider checks, schema versions, platform strategy report, no secrets and no run content beyond keys/status — redaction tested with planted secrets.

### 2.5 Packaging (M7c)

electron-builder config: NSIS installer (`.exe`, per-user, no admin by default, no auto-run of anything downloaded) and `.deb` (Electron sandbox needs setuid/AppArmor care — the package postinst and docs handle `chrome-sandbox`); the app bundles Conductor's `dist/` (zero runtime dependencies → nothing else to ship); build runs in a Docker image on this macOS host (cross-building NSIS without wine uses the electron-builder Docker image); **a `.deb` install + launch smoke test under Xvfb in a container**, or reported unverified; the Windows `.exe` is built but **cannot be executed here**: reported *built, unverified*. A CI workflow file (matrix build on `windows-latest` + `ubuntu-latest`, artifact upload) is written but **never executed** and labelled unvalidated YAML.

### 2b. Review conditions — BINDING (Reviewer R-M7-1…4 + non-blocking; Security S-M7-1…S-M7-21)

1. **Build gating is per platform in code, and a record can only restrict (R-M7-1, S-M7-7; BEFORE-EDIT).** The `buildIsolationVerified` baseline becomes **per platform in code**: build is verified only where a live suite ran — **macOS today**; Linux and Windows build stay **disabled** until their own evidence is committed with the code. The host self-test record is **add-only, may only further restrict** (a failed or missing host self-test disables building on that host), and is bound to `{os, arch, hostname hash, gitPath, gitVersion, hash of the env/stub generation code, conductor version}` — any change invalidates it and a record copied from another machine (roaming profile, synced home) does not satisfy it. The self-test actually attempts a push to a scratch bare repo with the guard env and proves: the push is refused, no ref moved, no credential helper or askpass canary was invoked, and the effective config under the guard env lists no origin outside the guard set (on Windows this must show that the Git for Windows **system** config, which commonly sets `credential.helper`, is not loaded). A file that can *enable* building is the exact path Security closed in M2. M7-AC3 is restated accordingly.
2. **The real secret inventory (R-M7-2, S-M7-4; BEFORE-EDIT).** In v2 as committed Conductor stores **no** credentials (Linear gone, no Codex API-key mode). What it *handles*: environment passthroughs (`ANTHROPIC_*`, `CLAUDE_CODE_OAUTH_TOKEN`, `CURSOR_API_KEY`, per-repo `envPassthrough`, values read from copied `.env` files for redaction), the session OTP/cookie/CSRF (memory only) and the CLIs' own credential stores. `docs/SECRETS.md` states this inventory (including env passthrough on Windows, where a Start-menu app does not inherit a shell's variables) and a test greps the stores it names. The `safeStorage`/IPC secret plumbing is **built when the first stored secret exists**; when it is built: `safeStorage` lives in main only, never reachable from preload; secrets travel main → sidecar over the MessagePort only, are held in memory and registered with the redactor on arrival; the encrypted blob is 0600 in `userData`, versioned, length-capped; a `decryptString` failure is "absent", never a plaintext fallback; `isEncryptionAvailable()` false or a Linux backend of `basic_text`/`unknown` ⇒ refuse to store except through a **native `dialog.showMessageBox` consent in main** that records the backend name (asked again when it changes); the same rule covers the CLI (TTY confirm, **not settable through the HTTP API**); SECRETS.md says what this protects (other users, offline disk theft) and what it does not (same-user malware); Linux `secret-tool` by absolute path with constant attributes and the secret on stdin.
3. **Windows runner decision — complete (R-M7-3, S-M7-5, S-M7-6; BEFORE-EDIT).** (a) **No command is spawned by bare name**: each needed executable is resolved once at startup to an absolute path from system directories and absolute `PATH` entries that exist and are **not** inside any registered repo, worktree, Conductor home or temp dir (never the cwd or `.`); spawn by that absolute path only; the runner refuses bare names (static test); child `PATH` = absolute entries only, child `PATHEXT` = `.COM;.EXE`. (Reason: the Windows lookup order includes the child's cwd — libuv/CreateProcess behaviour, documented, **not verified here: no Windows host**.) (b) **No `shell:true` anywhere** (static test). A `.cmd`/`.bat` target is never spawned with arguments derived from agent, schema, repo or card text (CVE-2024-27980 class). npm-style shims are resolved by parsing the shim to an absolute `node.exe` + script pair (both inside the shim's directory); a shim that does not parse is refused with "unavailable on Windows (unverified)". (c) **Gate/install commands are argv-only:** each token must match a conservative whitelist (letters, digits, `_ @ + = : , . / \ -`); any `& | ; < > ^ % ! ( ) " ' backtick $ newline NUL` makes the command **refused with "write one command per gate entry"**, and config offers an explicit per-gate **Windows command** override. (d) If a `.cmd` target is unavoidable (e.g. `npm`), Conductor writes a command file into a private 0700 temp dir (`O_EXCL`) containing only the absolute path + whitelisted tokens, runs it as the absolute `%SystemRoot%\System32\cmd.exe` with `/d /s /c "<abs file>"`, and deletes it afterwards. (e) **Every agent argv value is listed with its Windows handling:** prompts go on stdin; Claude's `--json-schema` text, `--name` and `--model` are argv — the injection corpus runs against the **real argv builders**, not only the tokenizer. How each CLI (`claude`, `agent`, `codex`, `npm`/`pnpm`) launches on Windows (native `.exe`, `node <script>` from the shim, or refused) is stated per CLI. `COMSPEC` is set by Conductor to the absolute System32 path, not inherited; `taskkill` is the absolute System32 path, integer pid, only for pids Conductor spawned; terminal targets that build a shell string (`terminalCommand`) are hidden on win32.
4. **Packaging and hardening items (R-M7-4; BEFORE-EDIT).** (a) The **Electron version is pinned** and the embedded Node is proven to satisfy what `dist/` needs (the sidecar runs under Electron's Node, not the user's Node ≥ 22.18); the `dist/` smoke test runs under that version. (b) Fuses flipped at package time: `RunAsNode` off, `EnableNodeOptionsEnvironmentVariable` off, `EnableNodeCliInspectArguments` off, `EnableCookieEncryption` on, `OnlyLoadAppFromAsar` on, `EnableEmbeddedAsarIntegrityValidation` on, `GrantFileProtocolExtraPrivileges` off (names verified against the pinned `@electron/fuses`). (c) The server reads `ui/`, `prompts/*.md` and spawns helpers relative to `ROOT`: decide **`asar: false` or an explicit `asarUnpack` list** and test `dist/` from a relocated directory. (d) `tsconfig.build.json` and the `.ts` → `.js` specifier rewrite are listed in §3.
5. **Session hand-off (S-M7-1).** As in §2.3 (POST `/auth`, port 0, MessagePort). **Desktop mode never attaches to an already-running server or a configured fixed port** (a squatter would receive the OTP). The renderer uses a **non-persistent partition** (no `persist:` prefix) so the cookie never reaches disk; navigation history is cleared after sign-in.
6. **Frozen Electron hardening spec (S-M7-2).** `BrowserWindow`: `contextIsolation:true`, `sandbox:true`, `nodeIntegration:false` (workers and subframes too), `webviewTag:false`, `webSecurity:true`, `allowRunningInsecureContent:false`, `experimentalFeatures:false`, `devTools:false` in packaged builds, `navigateOnDragDrop:false`, non-persistent partition; `app.enableSandbox()` before ready. Applied to **every** webContents via `web-contents-created`: `will-navigate`, `will-redirect` and `will-frame-navigate` allow only the exact parsed origin `http://127.0.0.1:<port>`; `setWindowOpenHandler` always denies and, for a user-initiated `https:` URL without userinfo and ≤ 2048 characters, hands it to `shell.openExternal`; `will-attach-webview` prevented; permission request/check and device-permission handlers deny everything; `session.webRequest.onBeforeRequest` cancels anything outside the exact origin (including `ws:`/`wss:`); no custom protocol, no `setAsDefaultProtocolClient`, no file associations, no `file://` loads; no `--remote-debugging-port`, `--inspect` or `appendSwitch` (static test). The sidecar is `utilityProcess.fork` only (the `ELECTRON_RUN_AS_NODE` alternative is dropped).
7. **IPC and consent (S-M7-3).** Every `ipcMain.handle` validates that the sender is the main frame of the main window and that its origin equals the pinned origin, validates the payload against a schema with a size cap, and the channel list is exactly the documented set. **Prefer no preload**; if unavoidable it exposes individually named functions through `contextBridge` (no raw `ipcRenderer`, no `send(channel, …)` passthrough, no event objects). Consent dialogs and the diagnostics save path are **native dialogs in main**; the renderer supplies no path and no consent boolean.
8. **No control channel (S-M7-8).** `win32` control is `none`; the strategy never creates a named pipe or socket path on Windows (static test); desktop mode never calls `listenControl`; the CLI commands that depend on it (`open`, `stop`) print the reason on Windows (print the URL as the fallback).
9. **Windows private-dir and path semantics (S-M7-9).** The strategy provides `ensurePrivateDir`: the Conductor home must resolve under the user profile (`%LOCALAPPDATA%`); `CONDUCTOR_HOME` elsewhere is refused unless the user explicitly confirms; docs say there is no `chmod`-level guarantee. Repo/worktree paths: refuse UNC (`\\host\share`, `\\?\UNC\` — touching an attacker-named share leaks NTLM credentials); reject reserved device names, trailing dots/spaces, `:` (alternate data streams) and 8.3 `~N` segments in plan-declared paths; compare case-insensitively; long-path refusal with a reason; junction/symlink/`\\?\` cases in the path-rule corpus. `ensureRealDir` passes an explicit 0700 on POSIX. The per-OS default data directory is specified (macOS path unchanged).
10. **Download gate and supply chain (S-M7-10, D4; BEFORE-EDIT).** The permission request in chat names each artifact: Electron (exact version and expected SHA-256), electron-builder, `@electron/fuses`, NSIS/fpm tool bundles, the Docker image (**pinned by `@sha256:` digest, never a tag**; "run the full suite in a Linux container" is itself a download and is in the asked-for list) with approximate sizes and source hosts. **Nothing is downloaded or installed before a yes in chat; M7a needs none.** `desktop/` has its own `package.json` with exact versions and a committed lockfile with integrity hashes; install is `npm ci`; the root `package.json` keeps zero `dependencies` (test) and `src/` never imports desktop packages; lifecycle scripts: Electron's binary download script is run explicitly after the checksum is compared with values recorded in the repo, everything else with `--ignore-scripts`; `npm audit` output (informational) and the SHA-256 of every produced artifact are recorded.

12. **Clarifications from the rev-2 reviews (Security C7-1…C7-6, Reviewer M7 conditions; binding).**
   - **C7-1 — fuses vs `asar` (can break the build).** `OnlyLoadAppFromAsar` and `EnableEmbeddedAsarIntegrityValidation` require an asar archive, so **`asar: false` is not allowed** with them. Decision: package **with asar** and an explicit minimal `asarUnpack` list (only what must be a real file: `prompts/*.md`, `ui/**`, the helper scripts the sidecar spawns, `fixtures` excluded); `dist/` is smoke-tested from a relocated directory **after fuse flipping**, so a fuse that breaks loading fails the test. If asar cannot be made to work with the unpack list, the fallback is to drop those two fuses **explicitly in this plan** and say why — never a silent mismatch.
   - **C7-2 (stale rows).** §2.2 / §2.3 rows that still describe the Windows no-push cell as "gated on a passed host self-test record" are superseded by §2b-1: build is **disabled in code** on Linux and Windows until each has its own evidence; a record can only restrict.
   - **C7-3 — the self-test runs by itself.** Under §2b-1 a missing self-test record disables building. The local zero-quota no-push self-test therefore runs **automatically at first start and whenever its binding changes** (macOS upgrade, git upgrade, a changed home): it spends no quota, shows its progress and result in the dashboard banner, and never blocks planning/review/verification. A user whose OS or git changed is never left without building because nothing re-ran the test.
   - **C7-4 — the Windows `open` fallback must not mint an OTP without a session.** Any "open the dashboard" fallback (tray item, protocol-less launch, second-instance activation) only focuses the existing window or, when there is no window, creates one through the §2.3 hand-off (main mints nothing; the sidecar mints one OTP per window create and sends it only over the MessagePort). No route, URL or CLI path may return an OTP to a caller that has no session; static test over the route table.
   - **C7-5 (gate wording).** All of §2b binds **M7a** as well (strategy layer, runner decision, secret inventory, per-platform build gating); "M7a needs no download" does not mean "M7a is exempt from §2b".
   - **C7-6 — the Windows command override uses the same whitelist.** The per-gate **Windows command** override (§2b-3c) goes through the same token whitelist and refusal rules as any other gate command; it is configuration the user writes, but it is never exempt from the argv-only rule and is never combined with agent/schema/card text.
   - **Linux and Windows builds are disabled until each platform has its own evidence — and this is raised with the user as a decision BEFORE packaging (Reviewer).** A `.deb` or `.exe` that installs can plan, review and verify but **cannot build** (the builder baseline is macOS-only in code). The coverage rows and the final report say "**Partial: build disabled on this platform**", not "supported". Before any packaging work starts (M7b/M7c), the user is asked whether to (a) ship the preview with build disabled, (b) hold packaging until a platform's live evidence exists, or (c) provide a Linux/Windows host for the evidence run.

### 2.6 Measurable acceptance criteria

- **M7-AC1 (a)** The strategy layer exists; **all pre-M7 tests pass unchanged on macOS**; POSIX behaviour is byte-identical (snapshot tests for argv/env/commands per OS function).
- **M7-AC2 (a)** Windows logic units tested as pure functions: command tokenizer refusals (injection corpus: `& | ; ` $() %VAR% ^ newline`), `.cmd` resolution, env allow-list contents, path rules (drive/UNC/reserved names/long paths), command-file generation never contains unvalidated text, `taskkill` argv.
- **M7-AC3 (a)** Build capability is per platform in code (macOS only today); the host self-test record can only **restrict** (a missing/failed/copied record disables building on that host; nothing in any file can enable it) — tested with a fake record store, including a record copied from another host.
- **M7-AC4 (a)** `dist/` build runs with only Node and passes a smoke test (server starts, OTP login, API state).
- **M7-AC5 (b)** Shell core tests: window options object equals the hardened spec (a frozen-spec test), navigation/openExternal/permission handlers reject everything outside the allow-list (table tests), IPC channel list is exactly the documented set, `safeStorage` unreachable from preload (static test), no HTTP route/token/command-line secret added.
- **M7-AC6 (b/c)** Sidecar manager: start/stop/restart/crash-recovery, tray close keeps it running, quit stops it gracefully (fake sidecar).
- **M7-AC7 (c)** Diagnostics export contains no planted secret; secret inventory document present and matches the code (test greps the stores it names).
- **M7-AC8 (c)** `.deb` builds in a container and installs/launches under Xvfb (or is reported unverified); the NSIS `.exe` builds (or is reported not built) and is labelled **built, unverified**; CI YAML lint-parses and is labelled unvalidated.
- **M7-AC9** Final report states exactly what ran on which OS.

## 5. Testing Strategy

- **Extraction gate:** the full existing suite unchanged on macOS; snapshot tests of every OS-touching function's output on POSIX before/after.
- **Windows logic (any host):** injection corpora against the tokenizer and command-file generator, env/path rule tables, `taskkill` argv, secret-backend selection logic, self-test gating.
- **Shell core:** frozen window-spec test, handler tables, IPC allow-list, static tests (no `contextBridge` exposure of secrets; no new HTTP routes; no secrets in argv/env), sidecar manager with a fake child.
- **Packaging:** builds in containers where permitted; `.deb` install/launch smoke under Xvfb; checksums recorded; all artifacts labelled per the honesty rule.
- **Not run (stated):** anything on real Windows; any macOS `.dmg`/notarisation (out of scope); auto-update; the CI workflow.

## 6. Risks and Dependencies

- **Native-module-free secret storage on Windows** forces `safeStorage` (desktop only): the headless Windows CLI path is limited — documented.
- **Cross-building NSIS without wine** relies on a Docker image download; if refused or unavailable the `.exe` is reported *not built*.
- **Electron on Linux (`chrome-sandbox`/AppArmor/userns):** packaging must not silently disable the sandbox; if it cannot be kept, the `.deb` is reported unverified with the reason.
- **Scope/size:** M7a is valuable on its own (a safer, portable core); M7b/c depend on the user's permission and on tooling that cannot be fully validated on this machine.
