## Part B — M1b review

### What I checked and found sound

- Authorship and forgery. `POST /api/items/:key/comment` with a forged `author`/`createdBy`/`id` stores `author: 'user'` only; the board's `author` is derived from the actor, and the only caller that passes actor `'user'` is `board.user`. Every Conductor write goes through `Effects.apply` (`'conductor'`), `Engine.ensureProjectForRepo`/`createTask` use the user facade or project creation. The planner's "requester clarifications" come from `author === 'user'` only (`stages.ts:388`) and sit inside the `<untrusted source="task-card">` fence.
- Lane ownership (K2). `move` goes to `engine.applyHumanMove`, which accepts only `backlog|todo|done|canceled`, changes the run record first and lets the card follow from `laneForRun` through the pending-effect path; the lane is written directly only for cards with no run (`board.user.moveLane`, atomic with respect to the claim step because both are synchronous). Probes: no-run card -> `active/needs_you/review/__proto__/constructor` all `400 bad_lane`; card with a run -> `review` -> `400`, lane unchanged. The orphan rule never auto-resets a card in `active/needs_you/review` (listed in `ignored`), `claimable()` defaults to `work` only, `ask/research/bug/subtask` cards are never claimed, a bug child is `autoStart:false`, an imported card sets `run.untrusted` and `approvalGate` forces approval under every policy (`stages.ts` `required`).
- API hygiene. Body types: `null`, `[]`, `"str"`, numbers, `true` against every board route and `approve`: `400` or a harmless no-op, never a 500. `__proto__`/`constructor`/`toString` and `../ENG-1` as keys: `404`; project `repo: "../../etc"`: `400`; `__proto__` in a request body or in `PUT /api/settings`: no pollution; comment 20 001 chars and title 201 chars: `400`; `approve` requires an integer `rev` (missing, `1.5`, `"1"` -> `400`; stale -> `409 stale`). IDOR is not a concept here (single user; keys enumerable behind the session cookie and CSRF gate in `http.ts`, which is unchanged).
- Home marker. A `v1`-shaped data folder (the real-shape fixture) makes `ensureHome()` and `createRuntime()` throw and the folder is unchanged; an empty folder gets `home.json` (generation 2). The marker is trust-on-presence (a folder with `config.json` plus a planted `home.json` is accepted) — acceptable for same-user.
- Worktree namespace. Default root `.conductor-v2-worktrees`, branch `conductor-v2/<key>`, refs `refs/conductor-v2/...`. `createWorktree` against a v1-registered worktree at the same path (possible when `worktreeRoot` is set explicitly in both) throws "exists on <branch>, expected ..." and touches nothing. See B-2 for the hole that remains.
- Redaction at the board. All Conductor-authored text reaches the board through `Effects.enqueue` with the run's secret set (token shapes + the repo's `.env` values) and then the board's own redactor; the probe in S-11 shows no leak into comments, bug cards or events.
- Crash protocol pieces. Status change and effect records are one `RunStore.update` (K1); apply is idempotent through `<RUN>:<effKey>` idempotency keys; `recover()` re-queues `running`; startup flush is the first tick.

### Findings

#### B-1 (High, blocking) — Conductor writes `.conductor/plan.md` and `.conductor/diff.patch` through repo-controlled symlinks
Location: `src/pipeline/stages.ts:418-419` (plan) and `:805` (diff). Pre-existing at v1 (`56c7f2d`: `writeFileSync(join(run.worktree, '.conductor', 'plan.md'), md)`), unchanged by M1b, but it is the hostile-repo threat model's first sink and `fsutil.ts` already has the fix (`safeWriteInside`, used only for `.cursor/cli.json`).
Evidence (reproduced with the harness): a repo that tracks `.conductor/plan.md -> <victim>` and `.conductor/diff.patch -> <victim2>` is checked out into the worktree with those links; the run completes `ready` with no warning and both victim files are overwritten with the plan markdown and the builder's diff (e.g. `### Summary\nImplement ...`, `diff --git ...`).
Impact: arbitrary overwrite of any user-writable file with agent-influenced content. A hostile repo steers the planner into putting a line of its choosing in the plan; pointing the link at `~/.zshrc`, `~/.ssh/authorized_keys` or a launch agent turns that into code execution. `.conductor` is a protected directory only for the builder's diff scope, not for this write.
Fix: write both files with `safeWriteInside(worktree, '.conductor/plan.md', md)` (replaces a link in the way, `O_NOFOLLOW|O_EXCL`), and make `ensureWorkspace` fail closed if `.conductor` is not a real directory owned by the worktree. Test: tracked symlinks to a victim file -> victim unchanged, run proceeds.

#### B-2 (High, blocking) — a foreign `run.worktree` is trusted: v2 can work inside, reset or remove a v1 checkout
Location: `stages.ts:318-323` (`ensureWorkspace` skips `createWorktree` whenever `run.worktree` exists), `engine.ts:~395-400` (`rerunFromHuman` backs up and `resetToBase`s `run0.worktree`), `engine.ts` `cleanup`, `worktree.ts:848-875` (`removeWorktree`), `schema/run-migrations.ts` (`migrateRunV1ToV2` keeps `worktree`, `branch`, `baseSha`, `commitSha`, `lockfileHash`, sessions).
Evidence (reproduced with the harness; a v1-style checkout on branch `conductor/eng-1` with an uncommitted file):
- A v2 run whose `worktree`/`branch`/`baseSha` are the v1 values (what the migration preserves) and `retry`: v2 plans, builds and commits **inside the v1 checkout** — v1 branch HEAD moved (`3855fe3 ENG-1: Add the answer feature`), `.conductor/plan.md` and `.cursor/cli.json` written there.
- `removeWorktree(repo, <v1 checkout>, 'conductor/eng-2', {deleteBranch:true})`: the checkout is force-removed together with its uncommitted file, and only then does it throw "refusing to delete non-conductor branch" (the prefix check runs after the destructive step).
- `rerunFromHuman` on a non-`keepCommits` status would additionally `resetToBase` the v1 checkout.
So the K5 namespace only governs paths that `createWorktree` derives; it does not protect against a path that is already in the run record. That is exactly the import scenario (BAR-363 carries v1's worktree). Not exploitable today without an importer or a tampered `run.json`, but it is M1b code and the claim "v2 can never touch v1's checkout" does not hold.
Fix: (1) `migrateRunV1ToV2` moves `worktree`, `branch`, `baseSha`, `commitSha`, `lockfileHash`, `commitNote` and `sessions[].id` resume data under `legacy.workspace` and clears them; (2) a single `assertOwnWorkspace(run, repo)` used by `ensureWorkspace`, `rerunFromHuman`, `cleanup` and `build`: `run.worktree` must resolve to `join(worktreeRoot-or-default, repo.name, run.key)`, be registered, and be on `refs/heads/conductor-v2/...`, else `needs_human` "foreign workspace — refusing"; (3) `removeWorktree` checks the branch prefix (and path ownership) BEFORE `git worktree remove`. Test: v1-registered worktree with a dirty file + a run record pointing at it -> nothing changes, run goes to `needs_human`.

#### B-3 (Medium, blocking) — a board storage failure is treated as a permanent effect error: narration and bug cards are silently dropped, `storageProblem` stays null
Location: `src/pipeline/effects.ts` `apply()`, `permanent = e instanceof BoardError && e.code !== 'read_only'`. `Board.commit` now throws `BoardError('storage_failed' | 'closed' | 'full')`, which all count as permanent.
Evidence (reproduced, fault hook making the journal write fail, then `effects.comment` and `effects.subIssue`): both effects end `status: "done"` with `lastError` set, `engine.status().storageProblem` is `null`, the comment and the bug card never reach the board, and later writes fail with `storage_failed` until restart (after restart the dropped effects are not re-applied because they are marked done).
Impact: violates K3 (persistent write failure must surface and be retried, not give up) — the needs-you explanation, the plan comment, bug children and lane projections written during a disk-full episode are lost for good, with no banner.
Fix: classify permanent only for target-gone/validation codes (`not_found`, `bad_input`, `too_deep`, `archived`, `bad_parent`...); `storage_failed`, `closed`, `read_only`, `full` are transient: keep `pending`, back off, set `lastFailure`/`failedSince` so `storageProblem()` fires after 15 s. Test: failing board -> effect stays pending, banner appears, restart after recovery applies it exactly once.

#### B-4 (Medium, before M1c) — the board accepts values its own loader rejects (write/load asymmetry)
Location: `src/board/store.ts` write path vs `src/board/validate.ts` (`idemKey` <= 300, `stage` <= 64, titles <= 1000...).
Evidence (reproduced): `createItem` with a 400-char `idemKey`, `setLane(..., {stage: 80 chars})`, `addComment(..., {idemKey: 400 chars})` are all accepted; after a crash the op is the last line and is dropped as torn (acknowledged write lost, `.torn-` copy kept), and if any later write follows, the board refuses to start (`CorruptFileError`) until the journal is repaired by hand.
Impact: today every caller passes bounded constants, so it is latent; the M1c importer will supply externally derived idempotency keys and stages. A refusal to start is a total outage.
Fix: run `validateEntity` (and the `nextSeq` shape check) on every op in `commit()` before `journal.append`, so the write path can never produce a line the loader rejects; cap `idemKey`/`stage` at write time too.

#### B-5 (Low-Medium, before M1c) — a quarantined `run.json` re-opens its key over stale artifacts
Evidence (reproduced): truncated (syntax-corrupt) `run.json` -> `get()` null, file renamed, `has()` false, then `create()` succeeds and `readArtifact('plan-1.json')` returns the old approved plan; `baseline.json` and `gates-N.json` of the old run would also be reused (stale gate baseline can mask regressions). Mitigations that now exist: the card of such a run is in `active/needs_you/review`, which the orphan rule reports instead of re-claiming. Related edge: a new board that re-issues `ENG-1` while an old `runs/ENG-1` exists makes the engine abort the old run ("card was removed") and the new card is never claimed and not listed in `ignored`.
Fix: keep a tombstone (`run.json.corrupt-*` counts as "key reserved" in `has()`/`create()`), or move the whole directory aside on quarantine; list a no-run card whose key has a leftover run directory in `ignored`.

#### B-6 (Low-Medium) — raw agent text in `run.json`, `verdict-N.json` and `GET /api/runs/:key`
Evidence (reproduced): a verifier reply echoing a non-token-shaped `.env` value and a token leaves both in `run.bugs[].title/detail`, `verdict-1.json`, and in the `toDetail` response used by the dashboard; board and events are clean. Pre-existing (same in v1), but the invariant says "redacted before ... UI". The fix prompt to the builder also carries `bugs[].detail` verbatim (intended, same repo access).
Fix: redact on read in `toDetail` (plan JSON, verdicts, bugs, review) with the run's secret set, and redact `title/detail/evidence` when storing `BugRec`s; keep the builder-facing text as is only if that is a conscious decision.

#### B-7 (Medium, before v2 runs next to the live v1) — shared launchd label, cookie name and default port
Evidence (code, not executed because it would touch `~/Library/LaunchAgents`): `service.ts` `SERVICE_LABEL = 'com.techteam.conductor'` and `plistPath()` are v1's; `conductor service install` from v2 overwrites the user's live v1 launch agent and `conductor uninstall`/`service uninstall` removes it. `auth.ts` `COOKIE_NAME = 'conductor_session'` is host-scoped, so v1 on :4317 and v2 on :4318 sign each other out (K7-iii); default `ui.port` is still 4317.
Fix before the user can run v2 beside v1: label `com.techteam.conductor.v2` and its own plist name, cookie `conductor_v2_session`, default port 4318, and `service install` refusing when the v1 label is loaded.

#### B-8 (Low-Medium) — `uninstall --purge` has no home guard and no backup
`cli.ts:226-229` runs `rmSync(paths.home(), {recursive:true, force:true})` without `ensureHome()`/marker check. With `CONDUCTOR_HOME` pointing at the wrong folder (v1's `~/.conductor`, `$HOME`) it deletes it; with the right one it deletes the whole board (the user's work items) with no copy (backups live outside the home but none is taken). Fix: require the `home.json` marker, refuse `$HOME`, `/`, the v1 home and any path that is not a v2 home, and take a verified `backupPaths` copy (board + config) before deleting, or require `--yes` with the path echoed.

#### B-9 (Low, M1c condition) — migrated in-flight runs would resume by themselves
`migrateRunV1ToV2` keeps `status`/`next`/`planApproved`/`approvedBy`. Today a migrated run has `itemId: ''` so `project()` aborts it as an orphan (safe by accident). Once the M1c importer links it to a card, `recover()` + `schedule()` would restart a `queued/running/paused/failed` v1 run (a `--force` build) with v1's approval, without the user having opted in to v2 running it. The importer must convert every non-terminal imported run to `parked` or `needs_human` (user decides), drop `planApproved` when the plan artifact is not carried, and keep `untrusted` (already carried for `assignedPickup`).

#### B-10 (Low) — API strictness and surface
- `GET /api/board` returns up to 2000 items with full descriptions (<= 50 KB each) and unpaged milestones: up to ~100 MB per request; return truncated descriptions and page.
- `edit` with `description: null` clears the description (accepted as ""); the integrity check then halts a running card at the next stage, so it is safe, but a `null` should be a `400`. `integrity()` hashes the description only; a title edit mid-run is not detected.
- `boardStatus()` maps `full`, `storage_failed`, `closed` to `400`; `storage_failed` also echoes the underlying filesystem message (a path) to the client. Map to `507`/`503` with a fixed text; log the detail.
- `ApiDeps.board` is the full `Board`; the API only needs read methods plus `user`. Narrow the type (`Pick<Board, ...> & {user: UserBoard}`) so a future handler cannot reach `setLane`/`addComment(actor)`.
- Rendering: `neutralise()` strips only markdown images. The current UI renders text with no `innerHTML`, so comment bodies are safe today; the M1c board UI must keep rendering bodies as text or through a sanitising renderer with an https link allow-list.
- Old UI misuse check: it never calls `/api/items/*` or `/api/board`; its `approve` without `rev` now fails with `400` (fail-safe); `PUT /api/settings {pickupFromBacklog}` is ignored; links built from `url: ''` are harmless.
