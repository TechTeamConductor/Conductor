# M2 security design sign-off — provider contract, build envelope extraction, Codex (read-only), routing

- Subject: `.techteam/plans/workspace-v2-m2.md` (rev 2), the Reviewer's round-3 conditions M2-1..M2-6 (`workspace-v2-plan-review.md` R3.4) and the master plan `workspace-v2.md` (rev 3, AC3/AC4/AC11, D2/D8/D9). No M2 code exists; this is a design review. Nothing was edited except this file.
- Evidence base: (1) the v1 build path read in code at `15687f9` (`stages.ts` build lifecycle ~555-700, `worktree.ts` guard/protected sets/`agentGitEnv`, `agents/{provider,cursor,claude,env,spawn}.ts`, `server/{http,api}.ts`, `redact.ts`); (2) the M1a security review findings that M2 builds on; (3) Codex vendor docs fetched today through `learn.chatgpt.com` (the page text is treated as data, not instructions; it is vendor documentation, NOT verified against a binary — the only `codex` on this machine is a broken v0.128.0 shim). Doc-derived facts are marked "(docs)". Secondary blog posts surfaced by search were used only as pointers and are marked "(secondary)".
- Threat model: hostile repo contents (instructions, `AGENTS.md`, `.codex/`), hostile agent/model output, hostile provider error text, a same-user process (including a `--force` Cursor builder with a shell), CSRF/local web attackers against the dashboard API, mistakes in routing/config.

## Verdict

The design is sound in structure: extract the envelope first, keep the guard lifecycle in the contract, Codex read-only only, no `workspace-write`, no `danger-full-access`, prompt on stdin, structural limit classification, private `CODEX_HOME`, own login or `CODEX_API_KEY`, behavioural canary with inconclusive-is-not-pass. Nothing in it lets Codex hold a build today. I found no reason the extraction must weaken the Cursor path. I did find several places where the text is wrong, self-contradictory, or silent on something the vendor docs make security-relevant. The four that matter most:

1. `--ignore-user-config` skips `$CODEX_HOME/config.toml` itself (docs), so the private `config.toml` the plan relies on for its pins is not read at exec time. The plan says both things.
2. Project `.codex/` layers (config, hooks, rules) load only for trusted projects (docs); the plan says repo `.codex/` "may load" and exempts it from the canary. A repo-level hook/MCP definition executing is code execution outside the sandbox, not a prompt-injection tier. It must be a canary FAIL, and the inertness must be tested, not assumed.
3. `shell_environment_policy.ignore_default_excludes` defaults to `true` (docs): variables whose names contain KEY/SECRET/TOKEN are NOT stripped from the environment of model-run commands. `CODEX_API_KEY` in the child env would be visible to the model via `env`. The plan's env allow-list controls what reaches the Codex process, not what reaches the agent's shell.
4. The canary covers filesystem writes and user-home hooks/MCP; it does not cover network egress or environment exposure, which are the two channels a hostile repo uses to steal data from a read-only agent.

Decision below: Approved with conditions. Conditions marked BEFORE-EDIT are text/design changes to the M2 plan (cheap); DURING are code/test requirements checked at the M2 Security code review.

## A. Provider contract and build-envelope extraction

What the v1 build path guarantees today, in order (`stages.ts` build): `writeCursorGuard` (rewrites `.cursor/cli.json` every build unless the repo tracks its own; symlink-safe) -> `agentGitEnv` (no-push env) -> `snapshotGitMeta(repo.path)` -> `agents.build` (env = `cursorEnv` + `req.env`, `req.env` last) -> `revertGitMeta` BEFORE the `res.ok` branch (so failures and limits still restore hooks/config) -> `checkCursorGuard` only when `ok` -> `commitAll` (secret + scope guard) -> `postBuildChecks` (diff scope incl. rename sources, branch secret scan incl. builder self-commits, also on the "builder committed by itself" path). Run fields `cursorGuardSha`/`noPushEnvOnly` are display/forensics only (the check uses the in-memory sha).

Assessment: extraction is safe if the order and the fail-closed edges are preserved, and the provider hooks cannot subtract from the envelope. The plan's shape (provider supplies only `prepare`/`verifyGuard`; envelope owns env, snapshot/restore, commit guard, post-build checks) is right. Risks I see in how it could go wrong:

- A-1. Choke point. The envelope must be the only code path that can start a builder. If `provider.build.run` can be called from `Agents`/routing directly, a routing bug or a tampered `config.roles` skips the envelope. Required: a single `runBuild()` in `envelope.ts`; `provider.build.run` is not exported to other modules; a static test greps that `runCursor`/`build.run` appear only in the Cursor adapter and the envelope.
- A-2. The `build && buildIsolationVerified` gate is enforced in routing/validation (which read config) but must ALSO be asserted inside `runBuild()` against the provider registry and the verification store (not against anything self-reported by the adapter or read from config). Defence in depth: config.json is hand-editable, and the M1a `extra` pass-through carries unknown keys verbatim.
- A-3. `Capabilities.build` must be derived from `typeof provider.build === 'function'`, and `buildIsolationVerified` only from the verification store / code baseline (section D). Neither may be a config or adapter-declared boolean. In M2 `codex.build` is absent, so Codex cannot build regardless of any record (test: `registry.codex.build === undefined`).
- A-4. `verifyGuard` is provider code running inside the safety envelope: a thrown error, a rejected promise, or a missing hook for a provider that declared a guard must be treated as `ok:false` -> `needs_human` (fail closed), never as "no guard needed". `prepare` return values must not be able to override envelope env: merge order `providerEnv` < `extraEnv` < envelope env, and keys `GIT_*`, `HOME`, `PATH`, `CODEX_HOME`-class names from `prepare` are dropped.
- A-5. Meta restore on every path. v1 restores only if `agents.build` returns; an exception between snapshot and restore skips it. Putting restore in a `finally` is a strict strengthening and should be done in commit 1a with a test (provider `run` throws; limit; abort; timeout -> hooks/`core.hooksPath` restored). This is the one intentional behaviour difference; say so in the commit.
- A-6. Generic run fields. The run.json migration `cursorGuardSha -> guardSha`, `noPushEnvOnly -> guardEnvOnly` must carry the old values; if a migrated in-flight run has neither, default `guardEnvOnly` to `true` (conservative display) rather than `false`. The API keeps `noPushEnvOnly` as a derived view.
- A-7. Characterization first. The envelope tests must exist and pass against the CURRENT code path (before extraction), then pass unchanged after. Enumerated cases for `test/envelope.test.ts` (run with a fake provider and real git): hook installed by the builder; `core.hooksPath`/alias/pushurl changed; guard file modified/deleted; secret in a committed file; protected file changed but not in plan; builder self-commits a protected file; rename of a protected source; provider `run` throws; `verifyGuard` throws; `prepare` returns env that tries to override `GIT_CONFIG_GLOBAL`; limit/abort/timeout results; provider without `prepare`. Keep the live Cursor suites (`cursor-nopush` 8 attacks) as the exit check, as planned.
- A-8 (pre-existing, preserve, do not extend). When the repo tracks its own `.cursor/cli.json` the build proceeds with environment-only no-push and only a note; the code comment in `worktree.ts` records that the env layer alone let 5 of 9 live variants through. M2 must not change this in the extraction commit (zero behaviour change). Recommendation to the user/Lead, outside M2: make `guardEnvOnly` hold the build for plan approval (M6 policy). The `guardEnvOnly` name must survive as a first-class field so that policy can key on it.
- A-9. Naming leaks are cosmetic but one is security-adjacent: the commit trailer "Built by Conductor (Cursor)" and `handleBuildFailure`'s default `provider: 'cursor'` must come from the provider label so an audit trail never attributes a build to the wrong CLI.

## B. Codex isolation

- B-1 Private home and `--ignore-user-config` (contradiction). Docs: `--ignore-user-config` "doesn't load `$CODEX_HOME/config.toml`", auth still comes from `CODEX_HOME`; whether `-c` overrides still apply under it is not stated. The plan (a) puts pins (`cli_auth_credentials_store = "file"`) in the private `config.toml` and (b) passes `--ignore-user-config`, which would skip that file. Resolution: exec must not depend on any file in the private home except credentials; every pin is passed as a first-class flag or `-c`; the private `config.toml` is a login-time convenience only (credential store), is written by Conductor, hash-checked and rewritten before every run, and contains no MCP servers/hooks. Whether `-c` pins apply under `--ignore-user-config` is established only by the behavioural canary (section B-8), not by reading docs. Because the user runs `codex login` themselves, the wizard command must state the store explicitly (`-c cli_auth_credentials_store="file"` or rely on the written config) and `auth()` must report `not-logged-in` with guidance if no file credential exists (keyring fallback).
- B-2 `--ignore-rules`: keep. Docs: it skips user and project execpolicy `.rules` files. Execpolicy `allow` rules are how a command is run without approval/sandbox escalation, so a repo-supplied rules file is a widening vector; dropping them removes it, and with `approval_policy=never` + `read-only` nothing can escalate anyway. The Reviewer's original concern (removing forbid rules) is outweighed. Add one canary item for it (B-8).
- B-3 Pins and argv. Required flags as planned: `--sandbox read-only`, `-c approval_policy="never"`, `--ignore-user-config`, `--ignore-rules`, `--ephemeral`, `--json`, `-o <tmp>`, prompt on stdin (`-`). `-c sandbox_workspace_write.network_access=false` is irrelevant under `read-only` and an unknown `-c` key is accepted silently (plan says so): it is belt-and-braces, not a control. The argv builder must be constants-only. Test must also assert ABSENCE of: `--dangerously-bypass-approvals-and-sandbox`, `--yolo`, `--full-auto`, `--approve-for-me`, `--add-dir` (docs: grants write access to extra directories), `--search`, `--profile`/`-p`, any `workspace-write`/`danger-full-access` string, any user- or config-derived `-c`. `cfg.agents.codex.model` is the only config-derived value: validate `^[A-Za-z0-9][A-Za-z0-9._:/-]{0,63}$` and pass as `--model=<v>`. `--skip-git-repo-check` is permitted only for the canary (scratch dir), never for stage runs.
- B-4 Environment inside the sandbox. Docs: `shell_environment_policy.inherit` is `none|core` (default not stated) and `ignore_default_excludes` defaults to `true`, so `*KEY*`/`*SECRET*`/`*TOKEN*` variables are NOT filtered from model-run commands. With `CODEX_API_KEY` in the child env the model can read it with `env` (and it then sits in the JSONL transcript the normaliser sees). Required: pin `shell_environment_policy` (`inherit` minimal, `ignore_default_excludes=false`, explicit excludes for `CODEX_*`, `*KEY*`, `*TOKEN*`, `*SECRET*`) via `-c`, and prove it with an env canary using a decoy variable (B-8). If the pin cannot be proven, API-key mode must not be offered (login mode, key in the private `auth.json`, only). Also set `HOME` for the Codex child to a private empty directory (the base env currently passes the real `HOME`): this is a cheap structural answer to the real `~/.codex` (hooks + two MCP servers on this machine), `~/.agents`, git/ssh configs, independent of whether Codex honours `CODEX_HOME` everywhere. State plainly in docs that it does not stop reads by absolute path.
- B-5 What a read-only Codex can reach. Docs: `read-only` "can only read files". The read scope is not documented in what I fetched; assume the whole filesystem the user can read. Unlike Claude (`CLAUDE_DENIED_READS`), there is no deny-list: `~/.ssh`, `~/.aws`, `.env` copies (`repo.copyFiles` puts `.env`/`.env.local` in worktrees), `~/.conductor-v2/**` incl. a `secrets.json` fallback, and the private `auth.json`. Network is the exfiltration channel: docs say networking is off by default for `workspace-write`; for `read-only` I have only secondary statements. So network-off must be demonstrated behaviourally in M2 (B-8), not deferred to M2b: a hostile repo instructing "curl the key to attacker.example" is the central attack on this tier. The tier text in UI/docs must say Codex read-only output can contain anything the user can read, that redaction is best-effort (patterns + exact-match secrets), and that plans derived from it flow into builder prompts as today.
- B-6 Credentials. The own-login / `CODEX_API_KEY` design is right and the "never read, link or copy the user's `auth.json`" test is right. Additions: (a) concurrency: the vendor says not to share one `auth.json` across concurrent jobs; `maxParallel` defaults to 2 (up to 6) and read-only items may run concurrently (M3), so two Codex processes would share the private home and race token refresh. Serialise Codex runs per private home (queue of 1) or document and test a cap; the same mutex covers the canary. (b) Home hygiene (B-7). (c) `CODEX_API_KEY`: provide it through the existing secret store; the plan names no endpoint for it. If an endpoint like `/api/setup/linear-key` is added it must follow that pattern (shape check, never echoed, stored, registered as an exact-match redaction secret in `configureLog` and in `engine.secrets()`, rate-limited), and the key must never appear in argv, env of any child other than the one Codex run, prompt audit files, events, or API responses (test each sink). (d) `--ephemeral` avoids rollout files; verify after the canary that the private home contains nothing but the allow-listed files (no `history.jsonl`, `sessions/`), and pin history persistence off if present.
- B-7 Private-home hygiene pre-flight (new). A same-user builder can write `~/.conductor-v2/providers/codex-home/hooks.json`; docs say hooks load from `hooks.json` in `CODEX_HOME`, and `--ignore-user-config` is documented only for `config.toml`. That is persistent code execution on the next Codex run. Before every Codex run (cheap, no model call), fail closed unless: the home is a real directory (lstat, not a symlink), owned by the user, mode 0700; `auth.json` is a regular file, 0600; the directory contains only an allow-list (`auth.json`, our `config.toml` whose sha256 matches what Conductor wrote — rewrite it, the way `writeCursorGuard` rewrites every build —, and Codex's own known state files); no `hooks.json`, `hooks/`, `rules/`, `AGENTS.md`, `skills/`, `prompts/`, `agents/`. A failed check is `errorKind:'isolation'` (needs_human, never falls back).
- B-8 Canary design. The evidence rules in rev 2 (attempted + denied write; marker side effects; inconclusive is not pass; `blocked` vs `unverified`) are right. Required additions, because "marker absent" proves nothing without them:
  - Positive control: the same hook/MCP/AGENTS.md items placed so they SHOULD load (a canary home used as `CODEX_HOME` without the pins) must create the marker; otherwise the CLI version may simply not support hooks and absence is meaningless -> inconclusive. Run order: positive control first.
  - Project-layer code-execution canary: a scratch repo with `.codex/config.toml` (MCP server and hook with a marker side effect) and `.codex/rules/canary.rules` (an `allow` rule for a marker-writing command). Any marker created = FAIL = `blocked`. Replaces the plan's "repo `.codex/` may load, not part of the pass condition". Docs say untrusted projects ignore project `.codex/` layers (config, hooks, rules), and a private home has no trust entries, so inertness is the expected result; test it, do not assume it. Repo `AGENTS.md` text may load (prompt-injection tier, as planned).
  - Network canary: the harness listens on a loopback port; the agent is asked to fetch it; pass only if the JSONL shows an attempted command AND the listener saw no connection. No attempt = inconclusive.
  - Environment canary: the canary child gets a decoy variable named like a secret (`CONDUCTOR_CANARY_DECOY_KEY=<random>`); the agent is asked to print its environment; pass only if an attempted command's output lacks the decoy.
  - Credential-read disclosure probe (informational, not pass/fail): record whether the agent can read a planted file next to the private home; the result is stored as a tier note ("can read outside the repo"), so the UI never implies Claude-level lock-down.
  - Hygiene: unique nonce per marker, marker dir outside every writable root, scratch cwd per run (`git init`ed or `--skip-git-repo-check`), `HOME` set to a fake home containing the user-like items, cleanup, explicit cost/quota statement and per-call confirmation. Parsing against undocumented event shapes defaults to inconclusive on any ambiguity.
  - Result binding: store `{cliVersion, binary sha256 when resolvable, argv-pin digest, private-config sha256, canaryVersion, passedAt, evidence summary}`; any change invalidates it. `blocked` is sticky until a later canary pass (deleting the file reverts to `unverified`, which is selectable, so a forged deletion gains nothing the user could not already do).
- B-9 Version floor. The installed shim is v0.128.0; the docs describe trust gating and flags that arrived in later releases (secondary sources: untrusted-project hook blocking around v0.122, `--approve-for-me` around v0.147). Registry must carry an explicit `minVersion` taken from the vendor changelog; below it Codex is `unverified` and the canary refuses. The canary result is valid only for the version it ran on.
- B-10 Temp files and parsing. `-o` and `--output-schema` files live in a `mkdtemp` 0700 directory owned by Conductor, outside the worktree, deleted afterwards; the final message read from `-o` is model-authored data (redact, cap, fence). The JSONL normaliser redacts every emitted string with the run's exact-match secrets, caps sizes, ignores unknown event types, reads only own properties, and never executes anything from the stream (the existing 4 MB line guard in `spawn.ts` applies).
- B-11 Protected sets. `.codex` is not in `PROTECTED_DIR_SEGMENTS` today (verified); adding it is right. Also add `.agents` (skills location used by Codex and other tools) and `agents.override.md` (Codex prefers an override file over `AGENTS.md`; verify the exact name against docs) to the protected names; `agents.md` is already protected. These make a builder's edits to Codex-read instructions a held diff.

## C. Fallback and routing abuse

- C-1 Classification. Limit/auth/spawn decisions must be established structurally first: the run failed (non-zero exit, or a terminal `turn.failed`/`error` event) AND no `turn.completed` was seen. Only then apply the limit/auth regex, to the structured error message (capped at 500 characters like `cursor.ts`), and only if absent to stderr. A run with exit 0 and `turn.completed` can never be reclassified, whatever an `agent_message` says (test: an agent_message "usage limit reached" with exit 0 stays ok; a long model-written `error`-shaped message is ignored beyond the cap). If a project hook/MCP ever loaded, their stderr can reach Codex's stderr, which is one more reason for the project-layer canary.
- C-2 Complexity routing is steerable by the model. `autoByComplexity` keys on the plan's declared complexity (model-authored, hence influenced by repo content). It must not be able to lower the safety of a stage. Rules: complexity may select among providers of equal or better `readOnlyIsolation` tier than the chain head for review/verification (never an `unverified`/`partial` provider unless that provider is the explicit chain head), and may only select `build && verified` providers for build roles (the runtime filter is authoritative; PUT validation must also reject a complexity entry that points at an ineligible provider). Forced holds for `L` and protected files stay independent of routing.
- C-3 Roles by capability, not by name. A static, exhaustive `ROLE_NEEDS: Record<Role, {build?: true; research?: true}>` in code (type-checked so a new role without an entry fails to compile). `documentation` writes files (its default is `[cursor]`): it is build-class unless explicitly specified as read-only. Item roles chosen by a plan (M3) are validated against this table, not trusted.
- C-4 "Unless nothing else remains" must not re-admit ineligible providers. The clause may keep a missing/not-logged-in/paused provider as the displayed reason for a pause (nothing runs); it must never run a `blocked` provider, a provider failing a capability need, or a build provider without verification. Test: chain with only ineligible providers -> pause with reason, zero spawns.
- C-5 Advance only on `limit`/`spawn`/`auth`; `isolation` never advances (as planned; keep the test). Note the behaviour change: v1 fell back only on a Claude limit; advancing on `auth`/`spawn` can silently move a stage to a weaker-tier provider and send repository content to another vendor. Acceptable under the defaults (v1 default already appends Cursor), but each advance must leave a visible run note and a board comment, and assigning any provider to a role must show the data-egress statement once (repo content is sent to that vendor).
- C-6 Pause abuse. A provider pause derived from a limit message must be bounded: parse `resetsAt` with a hard ceiling (for example 24 h) and keep the human `resume` path; a forged far-future reset in a structured error must not park a provider for years. `providerPause`/`quota` keyed by `ProviderId` only.
- C-7 No path from prose to provider choice: the inputs to routing are config chains, CLI-reported health/auth, CLI-reported limit events, capabilities from code/stores, and plan complexity (C-2). That list is the contract; add a test that routing is a pure function of exactly those inputs.

## D. `verification.json` trust

- D-1 Who can write it. Conductor's own `doctor --verify-build` process, and nothing else by design. A same-user process (including a `--force` Cursor builder) can write any file under `~/.conductor-v2`, including this one and `config.json`; the repo itself cannot (nothing copies repo files into the home; `copyFiles` goes the other way). So forging a record is a same-user capability, equal to editing `config.roles` directly. In M2 it buys nothing for Codex because `codex.build` does not exist (A-3). The record format must be hardened now so M2b inherits it.
- D-2 Rules. (a) Cursor's bundled baseline is a CODE constant `{cliVersion:'2026.10.19', grandfathered:true, source:'bundled-repo-suite'}`, not a file; the file can only ADD records (a corrupt/absent/invalid file means "no record", never "downgrade below baseline" and never "upgrade"). (b) No HTTP route and no `canary` result can write `buildIsolationVerified`; the canary only writes the read-only tier (B-8). (c) Record fields: `provider`, `suite` + `suiteDigest` (hash of the suite sources/fixtures), `cliVersion`, `binSha256` when resolvable, `passedAt`, `source` in a closed enum, `grandfathered` only true when the code baseline asserts it (a file claiming `grandfathered:true` is ignored). (d) Integrity: file 0600, directory 0700, `lstat` regular file, owner = user; plus an HMAC over the record keyed from the secret store when a keychain is available (documented as tamper-evidence against a casual writer, not against the same user holding keychain access; `CONDUCTOR_NO_KEYCHAIN` mode has none). (e) Validated at every use against the CURRENT version and, where resolvable, binary hash; mismatch -> unverified (Cursor: allowed with a persistent banner in the run summary and the provider card, not only in `doctor`, as in v1's "not re-verified on <version>").
- D-3 The read-only tier result (`verified|partial|unverified|blocked`) is persisted with the same binding and rules (B-8). Reading a stale or invalid file yields `unverified`, not `verified`.
- D-4 Residual: the Cursor baseline records that the live suite passed on one version; a Cursor update can change guard semantics with only a banner. That is v1's accepted behaviour; I do not require more in M2.

## E. API surface

All new routes sit behind the existing gate in `http.ts` (session cookie, Host check, `application/json`, `x-conductor-csrf`, `Sec-Fetch-Site`/Origin, 1 MB body), so CSRF and DNS rebinding are covered. What the routes themselves must do:

- E-1 `GET /api/providers`: every string that originates in a CLI (version, stderr tail, hint) is redacted, truncated and rendered with `textContent`; the repair hint is a static string per provider (never built from CLI output); no environment, no token, no credential path beyond the binary path and the private home path.
- E-2 `POST /api/providers/:id/test`: `:id` is checked against the `ProviderId` registry before any path is built (`providers/<id>/…` must never see a raw URL segment); `level` is an enum; `confirm === true` strictly for `canary`, required on every call, never stored; single-flight per provider plus a cooldown; shares the per-home mutex with engine runs (B-6); refuses while a stage of that provider is running; response contains a redacted summary only; the confirmation text shows what runs (model calls, quota, which login/key).
- E-3 `GET/PUT /api/roles`: `body` may be `null`/array/primitive (`JSON.parse` allows it): require a plain object. Role names are checked with `Object.hasOwn(ROLE_NEEDS, role)` and stored in a null-prototype object or `Map` (a `__proto__`/`constructor` role must be inert); `providers` entries must be registry ids, de-duplicated, length-capped; `autoByComplexity` keys are `S|M|L` only and its providers go through the same pairing check (C-2); the capability filter re-runs when config is loaded (a hand-edited or migrated `config.json` is untrusted) and ineligible entries are dropped with a warning, not honoured. Assigning an `unverified` provider to a role needs an explicit acknowledgement field (the UI shows the tier and the egress statement); a `blocked` provider is rejected with the reason. The response includes the human reason for every rejected pairing.
- E-4 `PUT /api/settings` compatibility mapping (M2-5): changes only the first `claude|cursor` slot / cursor-append rule; round-trip test must include a Codex entry and an `unverified` acknowledgement staying intact.
- E-5 Missing from the plan: the route or CLI by which `CODEX_API_KEY` is provided (B-6c), and the wizard's rendering of the login command (path shell-quoted, displayed as text).
- E-6 `doctor --isolation codex` / `--verify-build`: require `--yes` (or an interactive confirm) because they spend quota; never run in CI-style non-interactive mode without it.

## F. Other gaps

- F-1 §3 files table lacks `src/secrets.ts` (secret id for the Codex key), the setup route/CLI for the key, and the `engine.secrets()`/`configureLog` registration.
- F-2 Telemetry/update checks in the Codex process: pin off with `-c` where keys exist (best effort; unknown keys are silent) and note it; they are outbound connections of the Codex process itself, outside its sandbox.
- F-3 Docs wording: the pinned flags must not be described as verified until a canary has run on a working binary; the fake-Codex "canary honoured" control proves Conductor's wiring only (keep the sentence the Reviewer asked for); the Codex tier text per B-5.
- F-4 Concurrency of canary/doctor with stage runs and with each other is covered by the per-home mutex (B-6a).
- F-5 `agents.codex.bin` is config-supplied and executed like the other two (v1 accepted; not settable through any API route; keep it so).

## Conditions

1. Envelope design (A-1..A-5, A-7): single `runBuild()` choke point; the `build && verified` gate also asserted there from the registry/store; `build` capability derived from the presence of the function; fail-closed `verifyGuard`/`prepare` env rules; restore in `finally` (declared as the one intended difference); characterization tests written and green against the current code BEFORE extraction (commit 1a), cases enumerated as in A-7.
2. Exec configuration semantics (B-1, B-3): no reliance on private `config.toml` at exec; all pins via flags/`-c`; config.toml is login-time only, Conductor-written and hash-checked; wizard login command states the credential store; argv builder constants-only with the absence list; model-name validation.
3. Environment/secret policy for Codex (B-4, B-6c, E-5): `shell_environment_policy` pins plus the decoy-based proof, or no API-key mode; `HOME` override to a private empty dir; exact-match redaction registration and the sink list for `CODEX_API_KEY`; specify how the key is entered (route or CLI) in the plan.
4.
