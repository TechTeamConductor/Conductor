## B. Design conditions 2-4, 6-8, 9-18

### Exec configuration, env and secrets (design conditions 2-3)
- Argv (condition 2): exactly `exec --json --sandbox read-only --ignore-user-config --ignore-rules --ephemeral -c approval_policy="never" -c sandbox_workspace_write.network_access=false -c shell_environment_policy.{inherit="core", ignore_default_excludes=false, exclude=[CODEX_*,*KEY*,*TOKEN*,*SECRET*,*PASSWORD*]} [--model=<v>] [--output-schema f] -o f -` with the prompt on stdin. My probe found none of `--dangerously-bypass-approvals-and-sandbox`, `--yolo`, `--full-auto`, `--approve-for-me`, `--add-dir`, `--search`, `--profile/-p`, `--skip-git-repo-check`, `workspace-write`, `danger-full-access`. The model name is the only config-derived value: `--dangerously-bypass-…`, `a b`, `x\nSHELL`, `-c`, empty, `../../etc`, 80 characters, `é` are all dropped; `ok.model-1:preview` passes. No reliance on the private `config.toml` at exec time (login-time only, rewritten/hash-checked before each run).
- Env and HOME (condition 3): with a hostile ambient environment (`OPENAI_API_KEY`, `CODEX_API_KEY`, `CODEX_HOME=/Users/real/.codex`, `ANTHROPIC_API_KEY`, `GH_TOKEN`, `AWS_SECRET_ACCESS_KEY`, `LINEAR_API_KEY`) the child gets only `CODEX_HOME` (private), `HOME` (a per-run empty scratch dir), `PATH`, `SHELL`, `USER`, `LOGNAME`, `TMPDIR`, `GIT_TERMINAL_PROMPT` and the proxy variables (a `user:pass@` proxy URL in `HTTPS_PROXY` is passed on — pre-existing base allow-list behaviour; the `inherit="core"` pin is what keeps it out of the agent's shell, unproven without a binary). Deviation accepted: no API-key mode, so no key can be in any env and no exact-match registration is needed.
- Temp files: `-o`/schema in a 0700 `mkdtemp` outside the worktree, removed after the run; the scratch HOME is under the 0700 `providers/tmp` and removed.

### Hygiene pre-flight (conditions 8, 10)
Probe results: clean ⇒ accepted; `hooks.json`, `hooks/`, `skills/`, `AGENTS.md`, `agents.override.md`, a hidden file, `memories/` or `rules/` with content, a symlinked `auth.json`, a symlinked `sessions` ⇒ refused with `errorKind: isolation` (never advances the chain); a hostile `config.toml` is overwritten with Conductor's; a 0755 home and a 0666 `auth.json` are tightened to 0700/0600. Gap F-4: entries whose NAMES are allowed are not inspected — `shell_snapshots/evil.sh`, `models_cache.json`, `cache/plugin.js`, `sessions/*` are accepted. Of these only a planted `models_cache.json` could plausibly carry instructions (it can hold per-model system text in current CLI versions per secondary sources — unverified here); a same-user builder can already do worse (edit `agents.codex.bin` in `config.json`), so this is defence in depth: delete the regenerable entries (`models_cache.json`, `shell_snapshots/`, `cache/`, `tmp/`, `.tmp/`) before each run, the way `config.toml` is rewritten.

### Normaliser and failure classification (conditions 12, C-1)
Reproduced with `classifyCodexFailure`: exit 0 + `turn.completed` ⇒ never a failure even when prose says "usage limit … 401 unauthorized"; exit 0 without `completed` and without structured errors ⇒ not a failure; limit/auth text is consulted only after a non-zero exit (or an `error`/`turn.failed` with no `turn.completed`), from the structured messages (each capped at 500 chars, result capped at 300) then stderr, never from `agent_message`; a limit never carries a reset time (`resetsAt: null` ⇒ 15 min … 6 h back-off) and any pause is capped at 24 h in the engine. Events: own-property reads only, unknown types ignored, every emitted string redacted with the run's exact-match secrets, command outputs kept in memory only. Small points: the `errors` array is unbounded (2 000 events classified in 6 ms — harmless; cap it anyway); a non-zero exit with `turn.completed` is still classified from text (acceptable: the exit code is the structural failure).

### Canary (conditions 4, 14)
Verified from the code and the evaluator (pure function, tested with crafted evidence): positive controls for hook, MCP and rule; user-like items in a decoy HOME and a project-level `.codex/` layer (hook, MCP, rule) in the scratch repo ⇒ any marker = FAIL ⇒ `blocked`; write needs an attempted, denied write with no file; network needs an attempted call and a loopback listener that saw nothing; env decoys (`CONDUCTOR_CANARY_DECOY_KEY`, `…_PLAIN`); credential-read is information only; every absence without a control is `inconclusive`; PASS needs all nine required items; binding = {CLI version, binary hash, argv digest, private-config hash, canary version}; `blocked` is sticky until a later pass, and an `inconclusive` run changes nothing; below `CODEX_MIN_VERSION` (0.128.0) the canary refuses. Findings:
- **F-1 (Medium) — the canary can produce a false PASS on the network item, and cannot realistically pass on anything else.** Reproduced with `evaluateCanary`:
  - `network`: a `curl` that does not exist in the sandbox (exit 127, "command not found") with the listener never hit ⇒ `PASS` (also for exit 7). A missing or blocked `curl` proves nothing about the network pin. Require a connection-failure exit (curl 6, 7, 28, 35, 52, 56) and a host-side control: Conductor itself runs the same `curl` invocation against the listener before the model run and must see a hit; otherwise `inconclusive`.
  - `env-decoy`: the matcher is `^(env|printenv)(\s|$)`; a real CLI reports shell-wrapped commands (`/bin/zsh -lc env`), which my crafted evidence shows is `inconclusive` (the stand-in emits bare commands). Safe, but the item can then never pass; match the command anywhere in a shell wrapper and prove it against a transcript captured from a real binary before relying on it.
  - control run: `ctrlHome` is a scratch `CODEX_HOME` that never receives credentials (no `auth.json`), so on a real install the control run most likely cannot reach the model, its hook/MCP/rule never fire, and every marker item is `inconclusive` (read from the code, not provable without a binary). Copying the private home's `auth.json` into the scratch home would risk rotating the refresh token in the copy (the divergence the design review warned about); the safer design is to place the control layer temporarily INSIDE the private home under the lock, run, and remove it in `finally` (a crash leaves a planted `hooks.json` that the pre-flight refuses, i.e. fail-closed).
  Net effect today: the canary fails safe except for the network false pass; the "partial" tier can only be reached through evidence that is not yet realistic. The honesty label ("unverified / not run") is correct and must stay until a real transcript has been used to tune the matchers.
- **F-5 (Low)** `binSha256` hashes the resolved launcher (the npm shim script), not the native vendor binary; the CLI version still binds the result, but a swapped native binary behind an unchanged shim version would not invalidate a stored pass. Hash the vendor binary when it can be located, or say so in the docs.

### Verification records (conditions 5, 13)
Probe: no file ⇒ `unverified`; a forged `pass` that matches the install ⇒ `partial` (same-user forgery buys only the tier Cursor holds, for READ-ONLY roles); a forged `build` record with extra fields (`grandfathered`, `buildIsolationVerified`) ⇒ Codex caps unchanged, `buildEligibility` false; `blocked` then `inconclusive` ⇒ `blocked`; `blocked` then a later `pass` ⇒ `partial`; a symlinked, foreign-owned, oversized or malformed file ⇒ no records. Fields are a closed set; paths are built only from registry ids. Deviation accepted: no HMAC — the file is bookkeeping and the only things forging it can buy are `partial` or (by deleting a `blocked`) `unverified`, both already selectable; the docs say so.

### Routing, API, protected sets (conditions 6, 7, 8)
- Routing is a pure function of {roles, CLI-reported health/auth, CLI-reported pauses, derived capabilities, tier, complexity}; `ROLE_NEEDS` exhaustive with `documentation` build-class; a blocked or capability-failing provider is never run (also not "as the last one"); complexity picks apply after the plan only, must be eligible, and never at a lower tier than the chain head for read-only roles; only `limit`/`spawn`/`auth` advance the chain (an `isolation` result from the home pre-flight stops the stage); the pause cap (24 h) is in place. Gap F-7 (Low): a hop to a weaker-tier provider leaves a run-event note ("falling back to … (read-only, ask mode …)") but no board comment as my condition asked.
- API: `:id` is checked against the registry first; bodies must be plain objects; `PUT /api/roles` is own-property/registry-id/pairing-checked with human reasons, requires `acknowledge` for a newly added `unverified` provider, refuses `blocked` and build-class pairings, re-runs `normalizeRoles` at load, and returns the data-egress notice; the canary needs `confirm === true` on every call, is single-flight per provider, refuses while stages run, has a 60 s cool-down (F-6: it is set only after a successful run, so a throwing canary can be re-triggered at once; set it before the run) and records only reports that carry a binding. Detail strings are redacted and truncated; the repair hint is a static constant (it hard-codes `~/.conductor-v2`, wrong when `CONDUCTOR_HOME` is overridden — cosmetic).
- Protected sets: `.codex`, `.agents`, `agents.override.md` (any case, any depth) are held when the plan does not list them; ancestors are scanned for `.codex`/`.agents`/`agents.override.md`. (`codex.md` and `.codexignore` are not protected; the vendor docs I read do not list them as instruction files.)

### Findings that need action
- **F-2 (Medium) — health/auth waits on the per-home lock, so the dashboard hangs while Codex works.** Reproduced: with a Codex stage (4 s hold) running, `codexAuth` returned after 4018 ms and `agentHealth(codex)` — what `GET /api/state` and `GET /api/providers` await when their 30 s health cache expires — after 3016 ms for a 3 s hold. A plan stage can hold the lock for its 20 minute timeout, the canary for up to 24 minutes. `login status` is a read; do not take the home lock for it (or use a try-lock and report the last known/`unknown` state immediately).
- **F-3 (Low)** freeze `envAllow` (and any other array on a registry object).
- **F-4 (Low)** purge regenerable entries of the private home before each run (above).
- **F-6 (Low)** cool-down before the run, not after.
- **F-7 (Low)** board comment for a fallback hop to a weaker tier.
- **F-8 (Info)** cap `fold.errors` (first 5) and keep the `CODEX_MIN_VERSION` provenance in the docs (it is the version the author's machine has, not a vendor-changelog floor).

## Decision

Decision (M2 security code review): Approved with conditions

Conditions (apply before Codex is assigned to any role on a machine with a working binary; none blocks merging the M2 code, because Codex is in no default chain, unverified, and not run here):
1. F-1: network leg of the canary requires a connection-failure exit AND a host-side control that the same `curl` reaches the listener; `env-decoy` matches shell-wrapped commands; the control layer runs authenticated (placed inside the private home under the lock, removed in `finally`); all matchers are validated against a transcript captured from a real binary before a PASS is trusted. Until then the tier can never be shown as better than "unverified".
2. F-2: `codexAuth`/health must not wait on the per-home lock (no lock for `login status`, or try-lock with last-known/`unknown`).
3. F-3, F-4, F-6: freeze `envAllow`; purge regenerable private-home entries before each run; start the canary cool-down before the run.
4. F-7, F-8, F-5: board comment on a weaker-tier hop; cap the errors array; hash the vendor binary or document the shim hash.
5. The documentation keeps stating "Codex has never run against a real binary here" (it does today) and the Providers panel keeps the "unverified" label until condition 1 is met with real evidence.
